# 发布故障：历史证据、推断与验收目标

整理日期：2026-10-25。本文依据用户提供的 2026-10-15 日志、截图及当前本地源码；尚未取得真实图片发布的完整客户端与云端对应日志。

后续进展：2026-10-25 已通过开发者工具连接真实云环境，完成两次图片发布和首页显示，版本从 0 增至 2，并核对第二次 publish 的成功返回。详见 [实际调试记录](实际调试记录-2026-10-25.md)。以下对旧版故障的分析仍限于历史证据，不能把新版本成功当作旧版根因已证实。

## 已经证实的事实

- 两次展开的请求 action 都是 getCurrent，分别约 46ms、61ms 完成。它们证明对应环境中的数据库读取正常，并非发布请求日志。
- 返回 imageUrl 为空、updatedAt 为 null、version 为 0，说明查询时该环境仍返回初始未发布状态。不能据此判断另一环境或更晚的请求状态。
- 手动调用旧版 publish，传 imageBase64 空字符串，返回 INVALID_IMAGE。说明该次小参数请求能到达旧版发布校验并把业务结果返回客户端；按对应旧版校验顺序，管理员及当前记录读取也已经通过。
- INVALID_IMAGE 的 stage: database.read 是最近一个被记录的阶段；不能把这个字段解读成数据库读取出错。空图片本来就应被拒绝。
- CLIENT_TIMEOUT 是本项目等待计时器生成的错误码，表示等待期间封装没有收到可用于完成请求的结果。它不等于云平台确认函数执行超时，也不证明函数没有执行。
- 实际选图约 513KB，低于本项目 2MB 限制。Base64 大约增加三分之一体积，不能仅凭这个大小断言触发了平台请求上限。

## 最可能的问题范围

优先排查旧版真实图片发布路径：读取本地图片并构造参数、调用 SDK 发送请求、请求传输以及回调或 Promise 结果处理。小参数请求成功而真实图片调用超时，说明两条路径的差异值得优先检查，但没有证据能进一步锁定某个 SDK、网络或参数大小故障。

如果真实失败那次已经由 callApi 的计时器报 CLIENT_TIMEOUT，说明流程至少进入了云调用封装，不能简单认定一直卡在此前的本地读文件步骤。

用户提供的已展开日志中没有真实图片对应的 publish 请求。若云环境、时间窗口和日志筛选均正确且完整，这更支持请求未到达所查看的函数执行入口；否则也可能是查看了不同请求、不同环境，或日志没有覆盖失败那次。两者目前不能排除。

空参数发布在图片校验处提前结束，并未验证旧版上传云存储或数据库提交。因此云端上传或写入故障仍是待排查项，但现有日志没有支持它们的直接证据。也不能把数据库读成功当作数据库写成功。

源码中存在页面显示、身份验证和发布后刷新等不同触发点，无定时轮询或自动循环重试发布。同一 RequestId 的多行日志不能重复计数。仅凭调用次数不能解释上传卡住。

## 本轮修改的性质

旧版：图片 Base64 随 publish 参数发送，由函数处理图片并提交记录。

新版：客户端使用 wx.cloud.uploadFile 上传文件，取得 fileID 后调用 publish；函数下载并检查该文件，随后条件更新 current 记录。

这是对疑似故障路径的替换，加上等待上限和分阶段诊断，不是已经证实旧版根因的修复结论。它引入了必须同步更新的配置：云存储只允许指定管理员向 uploads 目录写入。数据库仍禁止客户端读写。

## 真正需要验收的内容

1. 用户已确认微信开发者工具打开 `D:\wechat-image-board`，后续直接维护此目录；本目录 AppID 和云环境 ID 已填写并保留。仍需上传新版云函数，确认编译及部署指向同一个环境。此前 C 盘副本有占位配置，不能代表实际运行项目。
2. 使用原来约 513KB 的图片，观察原生上传是否返回 fileID，云存储是否存在对应文件。上传进度 100% 本身不是发布成功。
3. 对应 publish 日志应出现 database.read、storage.download、database.commit 的成功结果，且函数业务返回 ok: true。
4. 同一环境的 current 记录应保存新 fileID、服务端 updatedAt，version 从实际旧值增加 1；如果仍是初始记录，应从 0 变为 1。
5. getCurrent 返回可用图片地址，管理员和普通用户重新打开或刷新看到新图及更新时间；再次更换图片也能看到更新。
6. 普通用户不能上传或发布；上传、云调用或刷新失败后能退出等待，且不会自动重复发布。

已通过的本地模拟测试验证代码控制流程与约束，不能证明真实微信网络、云存储规则和部署版本均正确。只有完成上述真实环境验收才能确认本次问题已解决。

## 源码与 Git

实际项目原先没有 Git 仓库。权限修复后，已在 D 盘目录创建仓库，并先以提交 `f2d3cdd` 保存未经本轮修改的旧版 Base64 源码，再应用原生上传方案，单独记录后续提交。可用 `git diff f2d3cdd HEAD` 查看本轮修复。更早的修改仍无逐次历史。

压缩包是可选分发副本，源码与 Git 记录才是维护依据。修改本地文件不会自动部署云函数或更新已发布的小程序。
